# `app.py` を読み解く — 148行の「交通整理役」

## このファイルは何をしているのか

このアプリには10個のツールがありますが、**`app.py` 自体はツールを1つも実装していません**。やっていることは2つだけです。

1. サイドバー（左側の設定パネル）を描く
2. 選ばれたツールの画面を呼び出す

たとえるなら、ビルの**受付兼案内係**です。各フロアで何をやっているかは知らないけれど、「3階に行きたい」と言われたら3階のボタンを押してくれる。実際の仕事は `tools/` フォルダの中の各ファイルがやっています。

---

## 1. 「辞書」でルーティングする

まず目を引くのがこれです。

```python
PAGES = {
    "✍️ ブログ記事作成": blog.render,
    "📧 メール作成・返信": mail.render,
    "📝 要約": summarize.render,
    ...
}
```

Python の辞書は `{キー: 値}` の形ですが、ここでは**値が「関数そのもの」**になっています。`blog.render()` と括弧をつけていない点が重要です。

- `blog.render()` … 括弧あり = 「今すぐ実行して、結果をちょうだい」
- `blog.render` … 括弧なし = 「実行はしないで、その関数自体をちょうだい」

つまり `PAGES` は「**メニュー名 → 対応する処理**」の対応表です。これがあるおかげで、最後の `main()` がこう書けます。

```python
page = sidebar()      # サイドバーで選ばれたメニュー名が返ってくる
PAGES[page]()         # 対応する関数を取り出して、実行する
```

`PAGES[page]` で関数を取り出し、直後の `()` で実行しています。もしこの辞書がなければ、

```python
if page == "✍️ ブログ記事作成":
    blog.render()
elif page == "📧 メール作成・返信":
    mail.render()
elif ...  # あと8個続く
```

という `if` の行列を書くことになります。**ツールを追加するときに `PAGES` に1行足すだけで済む**のは、この設計のおかげです。

---

## 2. 大前提：Streamlit は「操作のたびに全部やり直す」

ここから先を理解するのに、Streamlit の最大の特徴を押さえる必要があります。

> **ユーザーが何か操作するたびに、`app.py` が上から下まで丸ごと再実行される。**

スライダーを1ミリ動かしただけでも、ファイル全体がもう一度実行されます。普通のプログラムの感覚だと「え、毎回全部？」と驚くところですが、Streamlit はこの潔さでコードの単純さを買っています。

ただし、これだと**変数の中身が毎回リセットされてしまう**。そこで登場するのが `st.session_state` です。

```python
st.session_state["api_key"] = key
```

これは Streamlit が用意した「**再実行をまたいで生き残る箱**」です。普通の変数は再実行のたびに消えますが、この箱に入れたものは残ります。ブラウザのタブを開いている間だけ有効な、一時的な保管庫だと思ってください。

この「毎回再実行される」という性質が、以下で出てくる不思議なコードの理由になっています。

---

## 3. `sidebar()` — 描く順番に意味がある

```python
st.divider()
# モデル一覧の取得にキーが要るので、APIキーの入力を先に描画する。
api_key_section()

st.divider()
model_selector()
```

ここでコメントが断っているとおり、**APIキーの欄を先に描いています**。順番を入れ替えると壊れます。

理由はこうです。モデルの一覧（`gemini-3.6-flash` など）は Google のサーバーに問い合わせて取得しますが、その問い合わせには**APIキーが必要**です。

Streamlit は上から順に実行するので、モデル選択を先に書いてしまうと、その時点ではまだキーが箱に入っていません。結果、毎回「キーがないから一覧を取れない」となってしまう。だから**キー → モデル**の順にしてあります。

`st.slider` や `st.checkbox` にある `key="temperature"` という指定は、「この部品の値を `st.session_state["temperature"]` という名前で保管しておいて」という意味です。こうしておくと、後から他のファイル（`core/config.py`）がその値を読み取れます。

## 4. `model_selector()` — 3つの防御が仕込まれている

```python
def model_selector() -> None:
    models = available_models()
    ids = list(models)

    if st.session_state.get("model_select") not in ids:
        st.session_state.pop("model_select", None)

    current = st.session_state.get("model")
    default_index = ids.index(current) if current in ids else 0
    chosen = st.selectbox("モデル", ids, index=default_index, key="model_select")

    override = (st.session_state.get("model_override") or "").strip()
    st.session_state["model"] = override or chosen
```

短い関数ですが、それぞれの行が**過去に実際に起きた事故**への対策になっています。

### ① モデル名を固定しない

`available_models()` は Google の API に「今使えるモデルを教えて」と聞きに行きます。かつてここには `gemini-2.5-flash` という名前が直接書いてありましたが、提供終了で404エラーになりました。名前は変わるものなので、**毎回聞きに行くのが正解**という判断です。

### ② 選択中のモデルが消えたときの後始末

```python
if st.session_state.get("model_select") not in ids:
    st.session_state.pop("model_select", None)
```

昨日まで選べたモデルが、今日は一覧から消えているかもしれません。そのとき「保管庫には残っているのに選択肢にはない」という矛盾が起き、Streamlit がエラーを出します。そこで**一覧にない値は先に捨てて**しまいます。

### ③ 逃げ道を用意する

```python
st.session_state["model"] = override or chosen
```

`override or chosen` は「`override` が空でなければそれを、空なら `chosen` を使う」という Python の書き方です。

一覧に出ないモデルを試したくなったとき、詳細設定の「モデルIDを直接指定」に手打ちすれば、一覧を無視してそれが使われます。**自動化が裏目に出たときのための手動ハンドル**です。

## 5. APIキーまわり — なぜ関数が3つもあるのか

ここが一番「なぜ？」と思う部分だと思います。たった1つの入力欄のために、関数が3つもあります。

```python
def entered_api_key() -> str:     # 入力値を読んで整える
def api_key_field() -> None:      # 入力欄を描く
def api_key_section() -> None:    # 状態に応じて出し分ける
```

**すべて、Streamlit のある仕様への対処です。**

> **画面に描かれなくなった部品の値は、Streamlit が捨ててしまう。**

最初は自然にこう書いていました。

```python
if キーが入力済み:
    st.success("設定済み")     # 入力欄を消して、メッセージだけ出す
else:
    st.text_input("APIキー")   # 未入力なら入力欄を出す
```

一見まともですが、これは**動きません**。キーを入力した瞬間に入力欄が画面から消え、その瞬間に**入力したキーも一緒に消える**からです。画面には「設定済み ✅」と出ているのに中身は空、という状態になりました。

今のコードはこう解決しています。

```python
if key and key.isascii():
    st.success("API キー: 設定済み", icon="✅")
    with st.expander("キーを変更する"):
        api_key_field()          # ← 折りたたみの中に描き続ける
else:
    api_key_field()
```

**入力欄を消さず、折りたたみの中にしまう**。折りたたまれていても「描画されている」扱いなので、値は生き残ります。見た目はすっきりしたまま、中身も保持される、という落としどころです。

### `entered_api_key()` が分離されている理由

```python
def entered_api_key() -> str:
    raw = st.session_state.get("api_key_input") or ""
    return normalize_api_key(raw)
```

コメントに「**描画前でも参照できる**」とあります。Streamlit は再実行を始める前に部品の値を用意してくれるので、`api_key_input`（入力欄そのものの値）は関数の一番最初から読めます。一方 `api_key`（書き写した先）は、入力欄を描いた後にしか更新されません。

「設定済み」と表示するかどうかの判断は入力欄を**描く前**に必要なので、前者を見る必要がある——というわけです。これを間違えると、キーを入れても表示が1テンポ遅れます。

`normalize_api_key()` は全角文字の混入対策です。IMEが全角のまま入力された `ＡＩｚａ` を `AIza` に直します（APIキーは半角英数字しか通らないため）。

## 6. `main()` — わずか4行

```python
def main() -> None:
    st.set_page_config(page_title=APP_TITLE, page_icon=APP_ICON, layout="wide")
    page = sidebar()
    PAGES[page]()
```

1. ブラウザのタブ名とアイコン、横幅いっぱいのレイアウトを設定
2. サイドバーを描いて、選ばれたメニュー名を受け取る
3. 対応する関数を実行

最後の

```python
if __name__ == "__main__":
    main()
```

は Python の定型句で、「このファイルが直接実行されたときだけ `main()` を動かす」という意味です。他のファイルから読み込まれただけのときは動きません。

## まとめ：このファイルから学べること

| 書き方 | 狙い |
| --- | --- |
| 辞書に関数を入れる | `if/elif` の行列を消し、追加を1行で済ませる |
| `session_state` | 再実行で消える変数を生き残らせる |
| 描画の順番を守る | 後で使う値を、先に用意しておく |
| 部品を消さない | 消すと値も消える仕様への対処 |
| 名前を固定しない | 外部サービスの都合で変わるものは毎回問い合わせる |

**148行のうち、純粋な「機能」は半分もありません。** 残りは、Streamlit の癖や外部サービスの変化に耐えるための備えです。動くコードと壊れないコードの差は、だいたいこういうところに出ます。
